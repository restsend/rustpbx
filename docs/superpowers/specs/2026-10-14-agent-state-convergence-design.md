# 多节点坐席状态一致性修复

## 目标与证据

复现并修复：坐席转接后进入事后处理，手动空闲已经成功，但另一节点仍保留原通话的忙碌状态；原通话稍后结束时广播事后处理，覆盖软电话收到的 SIP 状态。重复空闲请求成功却不能修正通知。

问题涉及已有的 CC 状态机、共享 presence 表、AMI 状态广播和 SIP Presence 投影，不重建状态系统，不改变软电话协议。

## 唯一有效状态

有共享数据库时，`cc_agent_presence` 中已提交的状态、并发数和关联状态历史构成有效快照。本地内存用于执行已有状态机，写入前先对齐共享快照；事务对现有 `cc_agents` 坐席行取得写锁，序列化共享表和历史的读取与提交。冲突或数据库失败时不发布成功事件，不写入虚假的状态历史，也不发送对应 SIP 通知。

没有数据库时保留原有单节点内存模式。每个坐席的现有 transition lock 串行化本地请求、定时器和集群快照；不持有 DashMap guard 跨 await。

呼叫自动状态必须在最新快照上核对原通话绑定。转接离席后的延迟挂机不得重新进入事后处理；旧通话的超时不得结束新通话的振铃、忙碌或事后处理。预留必须返回实际是否成功，避免将没有应用的状态写入当作预留成功。

## 通知与幂等

CC 的 SIP Presence 直接投影已提交快照，使用现有坐席到分机映射。CC 身份的无版本远端 Presence 不再直接写入 PresenceManager；CC 集群消息仅作为刷新提示，节点重新读取共享数据库的已提交状态后投影。普通 SIP 身份继续使用原 Presence 同步。

本地投影在状态转移锁下执行，停用 RWI 消费循环中的旧状态二次投影，防止延迟事件覆盖新状态。重复手动状态请求重新投影当前状态，但不增加版本、不重置状态时钟、不重复写历史、计时和业务事件。

远端旧版本和未提交快照不能覆盖新状态。最新已提交状态可以取代另一个节点以前写入的内存状态，不能继续将“曾经由本节点写过”当成永久所有权。集群通知丢失后，通过共享快照读取收敛。

## 现有结构与发布（不修改 DDL）

复用 `cc_agents` 的坐席行作为事务锁，不改变其值；复用 `cc_agent_presence` 保存当前状态和占用；复用 `cc_agent_status_history.id` 的追加顺序及 `call_id` 的原有通话绑定语义。状态与历史在同一事务内提交，旧自动事件首先读取最新状态，再执行既有通话绑定 guard。

SQLite 先执行坐席行的无变化 UPDATE，取得数据库写锁；MySQL/PostgreSQL 对该 UPDATE 取得行锁。事务失败或等待超时返回失败，内存和通知不先行变更。没有可靠旧历史的运行态不能伪造通话绑定；保留已验证的本地绑定或按既有恢复流程处理。

不新增字段、不修改字段类型、不新增迁移、不在运行时执行 DDL。保留 `--skip-migrate`。所有共享该表的节点必须协调升级，旧版本绕过事务锁的写入者不具备一致性保证；灰度期间如实保留这个限制。

## 验收

1. 两个真实 registry 共享数据库；一端转接离席并手动空闲，另一端未收到广播再执行原通话结束，最终仍为空闲，呼叫数归零，不产生第二次事后处理。
2. 两节点在同一秒竞争预留同一个坐席，只能一个预留成功；失败者不能发布成功状态或污染本地副本。
3. 真实 HTTP 状态入口、集群 hub 和 PresenceManager 覆盖 idle、away、dnd、offline、ringing、busy、wrapup；重复手动写入修正投影但保持历史与状态时钟。
4. 旧通话结束、旧事后处理定时器、乱序广播、数据库写失败有明确结果；正常通话和合法事后处理仍可开始与结束。
5. 直接在现有结构执行实际读写，不新增迁移；SQLite 实际读写验证，MySQL/PostgreSQL SQL 或实际后端验证范围如实报告。
6. 使用固定 fast-test 入口做 RED/GREEN，复用最终测试二进制扩大状态相关回归，再通过服务脚本构建并验证持续运行与监听端口。

## 呼叫所有权与恢复

同一通话的 Ringing → Busy → Wrapup 保留已提交 owner。手动结束事后处理、延迟下线、振铃无应答和定时器释放通过已有 AMI 操作入口发送到 owner；owner 在共享锁下重新检查通话和状态。请求失败、owner 不在 peer 配置中、owner 不可达时返回失败，不在接收节点冒充成功。

延迟下线和振铃恢复目标仍使用 owner 的原有内存元数据。同一通话转换保留这些意图，离开运行态或进入另一通话时清理。它们没有新增持久化字段，因此不宣称 owner 重启后仍保留这些意图。共享状态和通话历史本身持久化；故障节点的后续处置沿用已有过期恢复机制。

振铃 offer 的 alias 写入可能走另一条数据库连接，因此与坐席写事务分开：共享锁下核验通话 → 释放事务 → 注册 alias → 再次核验历史、通话和 owner，失败时释放 alias。避免 SQLite 或单连接池等待自身事务。

PUBLISH 过期和客户端发布使用同一 hub admission 入口，先提交/延迟 CC 状态，再通知。过期写入失败保留 deadline 以便后续重试。现有 SIP PUBLISH 响应处理仍会确认请求，数据库错误是否映射 SIP 错误码不在本补丁内；HTTP 手动状态和 AMI owner 操作传播实际错误。

## 收敛与上线条件

候选查询刷新既有路由范围，不自动改变该 adapter 的坐席集合。周期收敛刷新全部有效坐席，并在 ACD 快照读取前完成，以修正丢失通知后的 Idle/Away/Dnd 等缓存。旧事件和旧死通话恢复请求按调用者观察到的历史 ID、通话和 owner 校验，不能在函数内部重新采样观察值来放过新通话。

所有共享数据库的状态写入节点应协调升级，运行中的旧写入者不服从本补丁事务锁。peer 配置必须能映射既有 owner；无法映射的旧 hostname/custom owner 会安全返回失败，应在通话排空后的发布窗口清理旧运行态。服务启动保留 --skip-migrate，只使用已经准备好的表。补丁未增加或更改字段，也未改变厂商迁移内容。

隔离分支已对齐当前主工作目录提交及其全部记录的递归子模块，保留其他开发者的媒体改动和现有 CC 编译适配。正式构建和启动仅使用隔离目录、独立 SQLite 测试库、独立端口和独立日志。
